## Security Fixes

This release addresses security vulnerabilities in the following underlying components:

- **Operating system (SUSE Linux Micro)**: The BaseOS image was updated with the latest SUSE security patches for the Linux kernel, resolving the following vulnerabilities in the IPv4 networking code:

  - [CVE-2026-99999](https://www.suse.com/security/cve/CVE-2026-99999.html) (PwnEscape): The kernel now validates the checksum offset of IPv4 packets before completing the checksum. This vulnerability could allow a potential escape from a KVM guest to the host ([#11998](https://github.com/harvester/harvester/issues/11998)).

  - [CVE-2026-98432](https://www.suse.com/security/cve/CVE-2026-98432.html): The kernel now frees IPv4 options only after an RCU grace period. This fixes a race condition during the setup of new IPv4 TCP connections that results in a use-after-free and could allow remote code execution ([#12110](https://github.com/harvester/harvester/issues/12110)).

- **CA trust store (eMudhra CA compromise)**: In October 2026, the private keys of several eMudhra intermediate certificate authorities were found to be recoverable from their public certificates. An attacker who holds one of these keys can issue a certificate for any host name and impersonate any TLS server to a client that still trusts these intermediates. This release addresses the issue in the following components:

  - **Operating system (SUSE Linux Micro)**: The `ca-certificates-mozilla` package was updated so that Harvester nodes no longer trust the affected root certificates. For more information, see [CVE-2026-114406](https://www.suse.com/security/cve/CVE-2026-114406.html).

  - **Go toolchain (Harvester components)**: Harvester components were rebuilt with Go 1.26.10, which rejects the compromised intermediate certificates during certificate verification ([#12054](https://github.com/harvester/harvester/issues/12054)). For more information, see [CVE-2026-111943](https://www.suse.com/security/cve/CVE-2026-111943.html).

  If you applied the workaround described in the [knowledge base article](https://harvesterhci.io/kb/emudhra-ca-compromise), delete the `emudhra-blocklist` CloudInit resource and reboot the nodes after upgrading.

## Upgrade

Harvester only allows upgrades from supported versions. For more information about upgrade paths and procedures, see [Upgrading Harvester](https://docs.harvesterhci.io/v1.9/upgrade/index).

> [!IMPORTANT]
> Harvester no longer shuts down virtual machines without warning when their live migration fails during an upgrade.
>
> Starting with v1.7.0, Harvester automatically shut down virtual machines that could not be live-migrated during the pre-drain phase of a node upgrade so that the upgrade could proceed (see [PR #9326](https://github.com/harvester/harvester/pull/9326)). As a result, production virtual machines could be shut down without warning, and you had no way to prevent this.
>
> v1.9.1 adds the `shutdownVMOnMigrationFailure` field to the [`upgrade-config`](https://docs.harvesterhci.io/v1.9/advanced/index#upgrade-config) setting so that you can decide how Harvester handles these virtual machines. By default, Harvester does not shut down a virtual machine when its live migration fails.
>
> - `false` (default): The virtual machine keeps running, and the upgrade waits until the live migration succeeds or you stop the virtual machine manually.
>
> - `true`: Harvester shuts down the virtual machine to allow the upgrade to proceed, which is the previous behavior. You must start the virtual machine manually after the upgrade.
>
> The default value already applies when you upgrade to v1.9.1. To keep the previous behavior, set the field to `true` before starting the upgrade. The Harvester UI does not include this field yet, so you must use the command `kubectl edit settings.harvesterhci.io upgrade-config`.
>
> [Documentation](https://docs.harvesterhci.io/v1.9/upgrade/index#failed-live-migration-in-the-pre-drained-state) | [GitHub issue](https://github.com/harvester/harvester/issues/12036)

## Highlights

### Support for Bare-Metal Workloads (General Availability)

By enabling the `harvester-baremetal-container-workload` feature flag in Rancher, managed Harvester clusters are exposed as standard downstream Kubernetes clusters on the Rancher UI, allowing containerized applications to run directly on bare-metal nodes alongside virtual machines.

You can manage these container workloads alongside your virtual machine workloads using an external Rancher instance or a Rancher instance deployed on the Harvester cluster using the **rancher-k3k** add-on.

[Documentation](https://docs.harvesterhci.io/v1.9/rancher/baremetal-workload/) | [GitHub issue](https://github.com/harvester/harvester/issues/5820)

### K3k and Rancher-K3k Add-On (Experimental)

The **rancher-k3k** add-on allows you to run Rancher as a workload on a Harvester cluster and replaces the deprecated **rancher-vcluster** add-on. It requires the **k3k** add-on, which deploys the K3k controller. When you enable **rancher-k3k**, Harvester deploys a nested K3s cluster and automatically provisions a Rancher instance that you can use to manage the underlying Harvester cluster.

[Documentation](https://docs.harvesterhci.io/v1.9/advanced/addons/rancher-k3k) | [GitHub issue](https://github.com/harvester/harvester/issues/5820)


### LVM CSI Driver (General Availability)

The **harvester-csi-driver-lvm** add-on is now generally available in Harvester v1.9.1. It provisions node-local LVM volumes, requiring workloads to run on the node where their storage resides. Consequently, virtual machines using node-local LVM volumes do not support live migration.

Before upgrading to the GA release, back up all critical data and delete any LVM volumes created with pre-GA drivers. Pre-GA volumes are incompatible with the GA driver and cannot be recovered after upgrading.

[Documentation](https://docs.harvesterhci.io/v1.9/advanced/addons/lvm-local-storage) | [GitHub issue](https://github.com/harvester/harvester/issues/10564)


### Virtual Machine Auto Balance (General Availability) 

The Virtual Machine Auto Balance add-on is now generally available in Harvester. Leveraging the Kubernetes Descheduler, this add-on automatically rebalances virtual machine workloads across cluster nodes based on administrator-defined policies, improving cluster performance and preventing resource contention.

This release includes production-ready default configurations, full lifecycle management via the Harvester add-on framework, customizable node utilization thresholds, and built-in guards against activation on single-node clusters. When thresholds are exceeded, the add-on migrates eligible workloads to underutilized nodes while automatically protecting non-migratable virtual machines.

[Documentation](https://docs.harvesterhci.io/v1.9/advanced/addons/virtual-machine-auto-balance) | [GitHub issue](https://github.com/harvester/harvester/issues/10779)

## Deprecations and Removals

### `striped` Volume Type by LVM CSI Driver

Support for the `striped` volume type is deprecated in the GA release of the LVM CSI driver. This volume type lacks the efficient snapshot, clone, and restore capabilities required by CSI workflows. As a result, all LVM storage now requires a `dm-thin` StorageClass. Because in-place conversion is not supported, migrate your data from existing striped volumes before upgrading to a Harvester version that removes them entirely.

### rancher-vcluster Add-On

**rancher-vcluster** is deprecated in Harvester v1.9.1 and will be removed in v1.10.0. To run Rancher as a workload on a Harvester cluster, use the [**rancher-k3k**](https://docs.harvesterhci.io/v1.9/advanced/addons/rancher-k3k) add-on instead. Harvester does not migrate the data of an existing **rancher-vcluster** deployment to **rancher-k3k**, so you must import the Harvester cluster again and recreate your Rancher configuration.

[GitHub issue](https://github.com/harvester/harvester/issues/10650)
