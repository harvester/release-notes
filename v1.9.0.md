### Fully Supported Features

#### UI-based Configuration of Pod Security Standards

Harvester v1.9.0 simplifies cluster-wide governance by allowing administrators to apply Kubernetes Pod Security Standards (PSS) directly from the UI using the new `cluster-pod-security-standard` setting. Once enabled, administrators can enforce specific security profiles across their environment by configuring the `Whitelisted Namespaces`, `Privileged Namespaces`, and `Restricted Namespaces` fields. To protect core system operations and guarantee the stability of Harvester, system namespaces are automatically locked and exempted from custom PSS modifications.

[GitHub issue](https://github.com/harvester/harvester/issues/10350)

#### Configurable Virtual Machine Startup Behavior After Creation

In earlier Harvester releases, virtual machines created from a snapshot, clone, or backup automatically start immediately after creation. In v1.9.0, you can keep these virtual machines powered off by selecting the **Remain halted** option on the UI or or setting `haltAfterRestore: true` in the resource manifest.

[GitHub issue](https://github.com/harvester/harvester/issues/10422)

#### Editable Virtual Machine Display Names

On the Harvester v1.9.0 UI, the virtual machine creation screen includes a **Display Name** field, which allows flexible labeling without strict character type or length restrictions. It is distinct from the **Name** field, which defines the custom resource name and must adhere to standard Kubernetes naming conventions. It also differs from the **Hostname** field, which defines the virtual machine's hostname inside the guest operating system and can be used to create unique DNS records. You can update the display name at any point in the virtual machine's lifecycle without affecting its configuration.

[GitHub issue](https://github.com/harvester/harvester/issues/10423)

## Deprecations and Removals

### rancher-vcluster Add-On

**rancher-vcluster** is deprecated in Harvester v1.9.0. To run Rancher as a workload on a Harvester cluster, use the **rancher-k3k** add-on instead. **rancher-k3k** provisions a nested K3s cluster in the `rancher-k3k` namespace and deploys Rancher onto it.
