# Harvester v1.9.0 Release Notes

This release introduces several features, enhancements, and bug fixes that improve system quality and the overall user experience. The documentation is available at https://docs.harvesterhci.io/v1.9.

The Harvester team appreciates your contributions and looks forward to receiving feedback regarding this release.

## Highlights

### Experimental Features



### Fully Supported Features

#### Parallel Live Migrations

Harvester v1.9.0 introduces support for concurrent multi-virtual machine live migration. The **Virtual Machines** screen on the UI allows you to select multiple virtual machines and initiate a migration for the entire group. On the migration dialog, selected virtual machines are grouped by their current node, allowing you to identify a target destination. Once initiated, Harvester processes a batch of migrations concurrently and automatically starts migrating the remaining virtual machines as active migrations complete. This simplifies host maintenance and workload rebalancing across your cluster.

[GitHub issue](https://github.com/harvester/harvester/issues/10425)

#### Support for Containerized GPU Workloads on Harvester Nodes

Starting with v1.9.0, you can run containerized GPU workloads directly on Harvester nodes alongside virtual machine-based GPU workloads. To separate these nodes, you must apply designated labels and deploy the NVIDIA GPU Operator to the Harvester cluster. The operator automatically targets only the nodes designated for bare-metal workloads, enabling native container access to GPU resources while leaving the remaining nodes available for vGPU-enabled virtual machines.

[GitHub issue](https://github.com/harvester/harvester/issues/5321)

#### Kubernetes Service Account Mounting

Harvester v1.9.0 introduces the ability to mount Kubernetes service accounts directly into virtual machines as live filesystems using virtiofs. You can now provide your virtual machine workloads with a secure Kubernetes identity to interact directly with the cluster API (to query pods, services, or secrets) without managing manual credentials. When configuring disks for a virtual machine via the UI, you can select **Filesystem** to mount a ServiceAccount, Secret, or ConfigMap object onto the guest operating system. Because virtiofs maintains a live projected filesystem, token rotations and RBAC permission changes are updated inside the virtual machine in real time without requiring a reboot.

[GitHub issue](https://github.com/harvester/harvester/issues/10426)

#### Load Balancers on Non-Management Interfaces for Guest Clusters

Previously, load balancer virtual IPs always bound to the primary management interface, blending workload and cluster management traffic. Starting with Harvester v1.9.0, you can route load balancer traffic through secondary VM networks. When creating a `LoadBalancer` service on the UI, you can select a specific VM network in both **DHCP** and **Pool** modes to bind the virtual IP to the correct interface. Note that target VM networks must be assigned to the exact same interface position across all nodes. Mismatched network ordering can be resolved by updating the interface layout in your machine pool settings.

[GitHub issue](https://github.com/harvester/harvester/issues/5486)

#### CPU Model Selection for Guest Clusters

Starting with Harvester v1.9.0, you can select custom CPU models when provisioning guest clusters using the Harvester Node Driver. When creating a cluster, the new CPU Model dropdown list allows you to choose `Default`, host-model, host-passthrough, or a specific CPU model. For named CPU models, the UI displays node availability next to each entry (for example, `Ready nodes: 1`), helping you select a compatible configuration and ensure consistent CPU capabilities across guest nodes.

[GitHub issue](https://github.com/harvester/harvester/issues/9744)

#### UI-based Configuration of Pod Security Standards

Harvester v1.9.0 simplifies cluster-wide governance by allowing administrators to apply Kubernetes Pod Security Standards (PSS) directly from the UI using the new `cluster-pod-security-standard` setting. Once enabled, administrators can enforce specific security profiles across their environment by configuring the `Whitelisted Namespaces`, `Privileged Namespaces`, and `Restricted Namespaces` fields. To protect core system operations and guarantee the stability of Harvester, system namespaces are automatically locked and exempted from custom PSS modifications.

[GitHub issue](https://github.com/harvester/harvester/issues/10350)

#### Configurable Virtual Machine Startup Behavior After Creation

In earlier Harvester releases, virtual machines created from a snapshot, clone, or backup automatically start immediately after creation. In v1.9.0, you can keep these virtual machines powered off by selecting the **Remain halted** option on the UI or or setting `haltAfterRestore: true` in the resource manifest.

[GitHub issue](https://github.com/harvester/harvester/issues/10422)

#### Visibility of Management Interface Details

Starting with v1.9.0, the **Cluster Network Configuration** screen provides enhanced visibility into management network interfaces for all non-witness nodes. You can now view essential configuration details for `mgmt-bo` directly on the UI, such as member interfaces, MTU size, and active bond mode, allowing you to inspect host networking and verify settings without risking direct interface changes.

[GitHub issue](https://github.com/harvester/harvester/issues/6110)

#### Editable Virtual Machine Display Names

On the Harvester v1.9.0 UI, the virtual machine creation screen includes a **Display Name** field, which allows flexible labeling without strict character type or length restrictions. It is distinct from the **Name** field, which defines the custom resource name and must adhere to standard Kubernetes naming conventions. It also differs from the **Hostname** field, which defines the virtual machine's hostname inside the guest operating system and can be used to create unique DNS records. You can update the display name at any point in the virtual machine's lifecycle without affecting its configuration.

[GitHub issue](https://github.com/harvester/harvester/issues/10423)

## Deprecations and Removals

### rancher-vcluster Add-On

**rancher-vcluster** is deprecated in Harvester v1.9.0. To run Rancher as a workload on a Harvester cluster, use the **rancher-k3k** add-on instead. **rancher-k3k** provisions a nested K3s cluster in the `rancher-k3k` namespace and deploys Rancher onto it.

### `ssl-parameters` Setting

The `ssl-parameters` setting for the Ingress NGINX Controller (`ingress-nginx`) is deprecated in Harvester v1.9.0 and replaced with the `traefik-default-tls-options` setting, which applies default [TLS options](https://doc.traefik.io/traefik/reference/routing-configuration/http/tls/tls-options/) for the Traefik Ingress Controller.
